The problems you named

Three of them, and my first read on each

Your posting names real work in flight instead of a wish list, which is rare enough that I want to respond to the actual problems. These are opening positions written from the outside, with none of your context. I expect to be wrong about some of it, and I'd want the first month to be mostly listening.

Identity resolution is a definition problem wearing a schema problem's clothes.

The first thing I'd do is not touch the data model. I'd get registry, shop, and health in a room and make each one write down what "the same person" means to them, because that definition is almost always where the real disagreement lives. Registry has a person who might be two people sharing an account. Shop has a person who is really a payment method and an address. Health has a person who is a person, legally and medically, and cannot be approximated.

That last one changes the rules for everything upstream. A wrong merge in a health context is not a data quality bug, it's a trust failure, and it's the kind a family does not forgive. So the design constraint I'd start from is that every merge has to be reversible and every merge has to be explainable after the fact, which means an event log and a stable identity key rather than mutating records in place.

Then I'd put the resolver behind an interface that returns a confidence score rather than a boolean, run it read-only in shadow mode against known-good pairs first, and measure it before a single merge is real. The ambiguous middle band goes to a human review lane, and the size of that band is the metric I'd report on. If nobody can tell me what precision we're getting today, we're not ready to write.

What backs this

In FieldCommand I built tenant isolation and role-based access on Postgres and Supabase, so I've lived in the version of this where one boundary mistake shows a customer somebody else's data.

Veritas is entirely this problem in another costume. It decides whether a legal citation and a real court record are the same thing, and it ships hedged verdicts on purpose, because the cost of a confident wrong answer is much higher than the cost of saying we could not confirm it.

This one is the thing I've spent the most of my own time on, and I got it wrong first.

My early instinct was that a coding agent underperforms because it doesn't know enough, so I wrote more documentation and loaded more of it. That made output worse in a way that was hard to see. More context made the agent more confident without making it more correct, and confident plus wrong is the expensive combination. I only caught it because I started checking output against something deterministic instead of reading it and nodding.

So I'd treat "how much context helps before it hurts" as an empirical question with an eval harness, not a documentation project. Hold a fixed set of representative tasks, vary what gets loaded, score the output with checks a machine can run rather than a human impression. The answer is going to be different per domain and it's going to move every time the models move, which means the harness matters more than whatever number it gives you this quarter.

The structural half of my answer is scoping. In AndrewOS, knowledge is organized by domain, and an agent loads the slice for the domain it's working in rather than the whole corpus. Underneath that sits a deterministic lint and gate layer that machine-checks output before a human ever reads it, structured traces so any run is replayable top to bottom, and one rule I hold hard: no agent reviews its own work. A reviewer running in the producer's context approves almost anything.

What backs this

AndrewOS is not a side project I describe in interviews, it's the thing I actually operate on. It runs scheduled autonomous loops, it delegates across agent layers, and it stops itself at defined human checkpoints. It isn't public, and I'd walk anyone at Babylist through it live.

The part I'd bring on day one is the deterministic gate. Agents are excellent at producing text that reads as correct. A machine check does not care how it reads.

Fixed deadline means scope is the variable. Rigor is not.

When the date can't move, the only honest question is what the smallest real version of this product is, and the job on week one is getting that written down and agreed to by the people who will later be disappointed. Not a roadmap. One page saying what ships and what does not, so that when we cut something in week six it's a decision we already made rather than a fight.

Money software has a floor you cannot ship below, and it isn't features. It's correctness, reversibility, and failure states a normal person can understand. So I'd cut features, not rigor. The parts that touch money I'd write and test by hand with adversarial cases, and let agents carry the volume around them: the surfaces, the states, the plumbing, the tests I'd have skipped if I were tired.

Then I'd get it in front of a small group of real families early, and stay on the hook for whether it helped them rather than whether it launched. A finance product that launches on time and nobody trusts is a worse outcome than one that slips.

The work

The list

You build the best list in the business, so I'll keep mine short and honest. Open any of these for the longer version, including the parts that didn't go well.

AndrewOS

Agent operating system · built and operated daily · not public

An operating system for running my own work through agents. Domain-scoped knowledge, layered delegation, scheduled autonomous loops, a deterministic lint and gate layer that machine-checks output before it ships, structured traces, and human gatekeeping at defined points.

This is the closest thing I have to your line about setting the standard for how a domain builds with AI, except nobody gave me the mandate, so I built it for myself and then it stuck.

The gate layer is what I'd bring first. Agent output arrives well-formed and plausible, which is exactly why human review of it degrades fast. Once a person reads something that reads well, they start agreeing with it. So the deterministic checks run before a human sees anything, and they're code rather than a prompt asking a model to be careful.

Traces make runs auditable. Every stage in the manager, builder, reviewer, validator chain appends what it received, what it decided, why, and what it handed off. A finished run reads top to bottom as an audit record instead of a wall of chat, which is the difference between debugging an agent system and guessing at one.

Independence is enforced structurally. A reviewer never runs inside the producer's context. It gets spawned fresh, with its own instructions, and for anything high stakes there are several running in parallel with different lenses. I learned this by watching same-context reviewers approve their own broken work with real enthusiasm.

The honest limit: this is a system built for one operator. Scaling it to a team of engineers with different habits is a genuinely different problem, and I'd expect to rebuild a lot of it.

FieldCommand

Multi-tenant SaaS for commercial trade contractors · solo build · currently parked

187,745 lines of TypeScript, written solo and AI-assisted end to end. Postgres and Supabase, Stripe billing, role-based access control, tenant isolation, and four AI features behind per-tenant feature flags.

I'm not going to tell you it's a hit. It's a launch-ready product that I parked when I took the Coder role, and I would rather say that plainly than dress up a graph. Parking it was the right call and it still stings a bit.

What it does prove is that I can hold a system that size in my head and ship it alone, including the parts nobody enjoys. Billing edge cases. Tenant boundaries. Permission matrices that have to be right on the first try because the failure mode is a contractor seeing a competitor's jobs.

It's also where I learned what agents are genuinely good at and where they quietly cost you. They are very good at volume, at surfaces, at the fifth variation of a form. They are dangerous anywhere the correct answer depends on a constraint that lives outside the file they're looking at, which is most of what makes multi-tenant software hard.

Veritas

Citation verification for legal filings · live product

A verification pipeline that checks cited cases and quotations in legal filings against source records. Hedged verdict semantics by design, and a fixture suite that gates every single release.

Lawyers have been sanctioned for filing briefs full of citations an AI invented. Veritas checks the filing before it goes to a judge.

The verdict language is the whole product. We never say a citation is fabricated or false. We say it was not located in the reporter, because that is the thing we can actually prove. The stronger word would convert better and it would also be a claim I cannot stand behind, so it's banned in the copy and banned in the output.

The fixture suite is a hard gate. A known set of bad citations has to come back with the right verdicts or the release does not ship. Not a guideline, not a checklist item somebody signs off on. The same discipline as catching output that's confidently wrong before it reaches a customer, applied here to somebody else's AI output rather than my own.

There's a second rule I'd bring anywhere: one firm's uploaded document is never reused in another firm's scan, permanently, even though it would make the product better. Some boundaries are worth more than the feature on the other side of them.

career-ops

Opinions I'll defend

You asked for strong opinions. Here are four.

Each of these cost me something to learn, which is the only reason I trust them.

Confidently wrong is the only failure mode left that matters.

Agents almost never fail loudly. They fail plausibly, in well-structured prose, with a reasonable-sounding justification. That's why review has to be deterministic and has to run before a human reads anything. Once a person reads output that reads well, they start agreeing with it.

More context is not more capability.

Past some point, loading more makes an agent more certain rather than more correct, and the curve is different for every domain. The only defensible answer to "how much context" comes from an eval harness you actually run, not from an intuition you had in a planning doc.

No agent should ever review its own work.

A reviewer running inside the producer's context will approve nearly anything, enthusiastically. Independence has to be structural, meaning a separate context with its own instructions, not a polite request in a prompt to be skeptical this time.

Prescribing the fix in a review is worse than naming the problem.

When I told reviewer agents how to fix what they found, defect rates went up sharply, because the fixer implemented the suggestion instead of understanding the bug. Now reviews state the finding and the fixer is explicitly allowed to reject the framing.
