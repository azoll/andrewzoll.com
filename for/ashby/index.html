Abhik, in the posting

"You've tackled projects with a lot of product and technical ambiguity, and you thrive at the intersection of the two. We're not building a simple CRUD app, and many of the challenges we tackle require you to use your knowledge of our customers to build powerful abstractions and flexibility in the system to solve a class of problems."

The abstraction I am proudest of exists because I got the specific version wrong first.

My early automation could send the same message to the same person twice. That is a bug that costs you a relationship rather than a request, and I had built it as a one-off check in one code path. The fix was to stop solving the instance and solve the class: a single deterministic guard, keyed on the recipient, that reads the live sent record, fails closed when it cannot read it, and refuses the send. Every outbound path now routes through it.

The same instinct produced the gate layer underneath my agents. Rather than asking each agent to behave, there is one machine-checkable rule set that everything generated has to clear before it can leave. Models decide what to say. Code decides whether it is allowed out.

I mention these rather than a feature list because your posting asks about a class of problems, and both of these started as one embarrassing instance.

Abhik, in the posting

"You know how to strike the right balance between speed and quality. Ashby wasn't built quickly. We took four years to launch publicly because convincing customers to switch required a high-quality product. However, time isn't infinite, especially for a startup."

I came from a job where being fast and wrong was a compliance event.

Before engineering I spent six years as a financial advisor under FINRA and SEC oversight, with real recordkeeping and audit requirements. That is a genuinely useful thing to have absorbed before writing software, because it teaches you which mistakes are recoverable and which ones are not, and those are not the same category.

It shows up directly in how I ship. Veritas gates every release on a fixed fixture suite, and correctness lives in deterministic code rather than model judgment, because a confident wrong answer about a court filing is worse than no answer. Meanwhile FieldCommand shipped four AI features behind per-tenant flags, which is the fast path, because a flag makes the mistake recoverable.

At Coder I own the quality practice for the platform I work on: test coverage, release process, and the operating docs the rest of the team works from. Two-person team, Python, large production codebase, shipping straight to prod.

Abhik, in the posting

"You seek to create leverage in your work... Your impatience usually leads to new abstractions, tools to allow Support to debug before Engineering, new lint rules to prevent common bugs, etc."

Your parenthetical about lint rules is the most specific thing in the posting, and it is the thing I would point at.

I wrote a linter. It catches the writing patterns I keep making, it runs on everything before it goes out under my name, and it exits non-zero rather than warning, because a warning is a suggestion and I will ignore my own suggestions.

Underneath that, every agent in my pipeline appends a structured trace: what it received, what it decided, why, and what it handed off. A finished run reads top to bottom as a replayable audit record. I built it so I could debug a run without rerunning it, which is the same reason you would want Support to debug before Engineering.

And no agent reviews its own work. A builder produces, and an independent reviewer runs in a separate context where it cannot quietly agree with itself. That rule exists because the first version did agree with itself, constantly, and was useless.
